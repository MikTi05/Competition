Решение соревнования Kaggle [Spaceship Titanic](https://www.kaggle.com/competitions/spaceship-titanic): полный цикл от исследовательского анализа данных до ансамбля из трёх моделей.

|---|---|
| **Задача** | бинарная классификация, метрика Accuracy |
| **Результат на Kaggle** | `0.80897`, место 191, примерно топ 11% |
| **Локальная оценка** | OOF Accuracy `0.8117` на 5-fold стратифицированной кросс-валидации |
| **Финальная модель** | среднее вероятностей Random Forest, Gradient Boosting и LightGBM |
| **Стек** | Python, pandas, scikit-learn, LightGBM, Matplotlib, seaborn |

Весь код, графики и промежуточные выводы находятся в ноутбуке [`spaceship_titanic_solution.ipynb`](spaceship_titanic_solution.ipynb).

## Что сделано

- Проведён разведочный анализ: пропуски, дубликаты, распределения, связь признаков с целевой переменной.
- Построено 11 новых признаков из `PassengerId`, `Cabin`, расходов и возраста.
- Вся предобработка собрана в `Pipeline` и `ColumnTransformer`, поэтому заполнение пропусков и кодирование обучаются только на тренировочных фолдах, без утечки данных.
- Пять моделей сравнены на одной и той же схеме кросс-валидации.
- Гиперпараметры LightGBM подобраны через `RandomizedSearchCV`; по ходу найдена и устранена проблема вложенной параллельности.
- Ансамбль оценён честно, по out-of-fold предсказаниям. Локальная оценка `0.8117` близка к результату на лидерборде `0.80897`.

## Постановка задачи

Нужно предсказать значение `Transported`: был ли пассажир перенесён в другое измерение.

- Тип задачи: бинарная классификация.
- Метрика соревнования: Accuracy.
- Обучающая выборка: 8693 объекта.
- Тестовая выборка: 4277 объектов.

## Ход решения

### 1. Исследовательский анализ данных

Проверены размеры и типы данных, распределение целевой переменной, пропуски, дубликаты и уникальность `PassengerId`, числовые и категориальные признаки.

Основные наблюдения:

- целевая переменная практически сбалансирована, поэтому Accuracy подходит как метрика без поправок;
- доля пропусков в отдельных столбцах не превышает примерно 2,5%;
- дубликатов нет, пассажиры из train и test не пересекаются;
- расходы содержат много нулей и имеют сильную правую асимметрию;
- `CryoSleep`, расходы, палуба и сторона каюты заметно связаны с целевой переменной.

Строки с пропусками не удалялись. Числовые признаки заполнялись медианой, категориальные самым частым значением.

### 2. Baseline

`LogisticRegression` на исходных признаках, оценка на пятикратной `StratifiedKFold` с перемешиванием и `random_state=42`.

- средняя Accuracy: `0.7860`;
- стандартное отклонение: `0.0096`.

### 3. Feature Engineering

| Источник | Признаки |
|---|---|
| `PassengerId` | `GroupId`, `GroupMemberNumber`, `GroupSize`, `IsAlone` |
| `Cabin` | `CabinDeck`, `CabinNumber`, `CabinSide` |
| Расходы | `TotalSpend`, `HasSpending` |
| `Age` | `AgeGroup` |
| Вся запись | `MissingCount` (число пропусков у пассажира) |

Та же Logistic Regression на расширенном наборе признаков:

- средняя Accuracy: `0.7908` (прирост `+0.0047`);
- стандартное отклонение: `0.0053`.

Качество выросло на четырёх фолдах из пяти, а разброс между фолдами уменьшился почти вдвое.

### 4. Сравнение моделей

Все модели оценивались на одинаковой пятикратной стратифицированной кросс-валидации.

| Модель | Средняя Accuracy | Стандартное отклонение |
|---|---:|---:|
| Logistic Regression, baseline | 0.7860 | 0.0096 |
| Logistic Regression + Feature Engineering | 0.7908 | 0.0053 |
| Random Forest | 0.8033 | 0.0090 |
| Gradient Boosting | 0.8063 | 0.0083 |
| LightGBM | 0.8093 | 0.0061 |
| LightGBM после подбора параметров | 0.8098 | 0.0067 |
| **Blend трёх лучших моделей** | **0.8117** | — |

Нелинейные модели заметно превзошли логистическую регрессию. Лучшей одиночной моделью стал настроенный LightGBM.

### 5. Подбор гиперпараметров LightGBM

Первый запуск `RandomizedSearchCV` (15 наборов параметров на 5 фолдах, то есть 75 обучений) не завершился за два с лишним часа. Причина: `n_jobs=-1` стоял одновременно и в поиске, и в `LGBMClassifier`, и вложенные процессы конкурировали за ядра.

Что было изменено:

- число наборов параметров уменьшено с 15 до 8;
- внутри поиска используется трёхкратная кросс-валидация;
- пространство параметров сокращено;
- в `LGBMClassifier` установлен `n_jobs=1`, параллельность оставлена только на уровне поиска;
- найденная модель повторно проверена на исходной пятикратной кросс-валидации.

Лучшие параметры:

```text
n_estimators      = 400
learning_rate     = 0.03
max_depth         = 4
num_leaves        = 15
min_child_samples = 20
colsample_bytree  = 0.9
```

Accuracy выросла с `0.8093` до `0.8098` (`+0.0006`). На обучающих фолдах модель даёт `0.8485`, на валидационных `0.8098`; разрыв `0.0386` говорит об умеренном переобучении.

### 6. Ансамблирование

Для каждой модели рассчитаны out-of-fold вероятности, на них проверены простое и взвешенное усреднение.

| Вариант | OOF Accuracy |
|---|---:|
| Среднее трёх моделей (RF + GB + LightGBM), равные веса | **0.8117** |
| Лучший взвешенный вариант (0.25 / 0.35 / 0.40) | 0.8105 |
| Настроенный LightGBM без ансамбля | 0.8098 |
| Среднее всех четырёх моделей | 0.8078 |

- Добавление Logistic Regression с равным весом ухудшило результат: её собственное качество (`0.7908`) существенно ниже остальных.
- Увеличение веса LightGBM не помогло, равные веса оказались лучшим вариантом.
- Прирост от ансамбля небольшой, потому что предсказания моделей сильно коррелируют: у Gradient Boosting и LightGBM корреляция около `0.976`.

### Финальное решение

```text
P(Transported) = (Random Forest + Gradient Boosting + LightGBM) / 3
```

Порог классификации `0.5`. Три модели обучены на всей обучающей выборке, предсказания ансамбля отличаются от предсказаний одиночного LightGBM на 194 объектах теста (4,5%).

| | Accuracy |
|---|---:|
| Локально, OOF | 0.8117 |
| Kaggle, leaderboard | 0.80897 |

Близость двух оценок показывает, что выбранная схема валидации адекватно оценивает обобщающую способность решения.

## Итоги

**Что дало результат**

1. Признаки из `PassengerId`, `Cabin` и расходов.
2. Переход от линейной модели к деревьям и градиентному бустингу: около `+0.02` Accuracy.
3. Простое усреднение трёх лучших моделей с равными весами.
4. Оценка ансамбля по OOF-предсказаниям и единый `Pipeline` для всей предобработки.

**Что не сработало или дало слабый эффект**

1. Feature Engineering дал логистической регрессии только `+0.0047`: часть новых признаков построена на уже используемых расходах.
2. Подбор гиперпараметров LightGBM улучшил Accuracy всего на `0.0006`.
3. Blending всех четырёх моделей опустил качество до `0.8078`.
4. Взвешенный blending не превзошёл простое усреднение.
5. Высокая корреляция бустингов ограничила выигрыш от ансамбля.

## Воспроизведение результата

Пути к данным в ноутбуке заданы для среды Kaggle, поэтому проще всего запускать его там.

1. Открыть соревнование [Spaceship Titanic](https://www.kaggle.com/competitions/spaceship-titanic) и создать Kaggle Notebook.
2. Подключить данные соревнования через `Add Input`.
3. Загрузить `spaceship_titanic_solution.ipynb` и выполнить все ячейки через `Run All`.
4. Отправить появившийся файл `/kaggle/working/submission.csv` через `Submit Prediction`.

Для локального запуска нужно установить зависимости, скачать данные соревнования и заменить пути `/kaggle/input/...` и `/kaggle/working/...` в ноутбуке на свои:

```bash
pip install -r requirements.txt
jupyter notebook spaceship_titanic_solution.ipynb
```
